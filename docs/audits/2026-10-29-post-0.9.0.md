# Audit complémentaire de tailwind-canonical 0.9.0

Date : 29 octobre 2026. Base : `825bac7307513debb039cdcc51aad90b230a28ed`.
Cette passe complète l’audit initial et examine les chemins qu’il ne couvrait pas.
Les corrections décrites sont locales : aucun commit, push ou nouvelle publication.

## Conclusion

Le principal point faible reste la confusion possible entre une simplification
syntaxique et une équivalence de rendu ou de comportement JavaScript. Cette passe
reproduit des corruptions de chaînes, de prédicats et de clés d’objets, ainsi que
des différences CSS liées aux priorités et aux axes logiques de Tailwind v4.
Les défauts non ambigus ont été corrigés et couverts par des régressions.
Le choix de préserver l’interligne a été appliqué : les tailles typographiques
ne sont plus converties par défaut, comme décrit ci-dessous.

Les tests existants étaient nombreux mais partageaient certaines hypothèses du
moteur. Des compilations réelles de Tailwind v3/v4 et des tests du JavaScript
produit complètent désormais ces tests. Ils vérifient les cas couverts ; ils ne
constituent pas une preuve pour toute combinaison de CSS, de thème ou de syntaxe.

## Décision appliquée : préserver la taille de texte et son interligne

Les compilateurs Tailwind 3.3.7 et 4.3.3 confirment cette différence :

```css
/* text-[12px] */
font-size: 12px;

/* text-xs, thème standard */
font-size: 0.75rem;
line-height: 1rem; /* v4 utilise ses variables de thème pour le même défaut */
```

Une police de même taille n’implique donc pas un rendu équivalent : l’interligne
hérité peut être remplacé. La documentation officielle précise que les tailles
nommées incluent aussi un interligne. [Source : font-size](https://tailwindcss.com/docs/font-size).
Le fait que les axes `px` et `py` soient logiques sous v4 est également explicite
dans la documentation. [Source : padding](https://tailwindcss.com/docs/padding).

L’utilisateur a choisi la préservation stricte du rendu. La conversion des tailles
arbitraires de texte en pixels et rem est donc désactivée par défaut dans le
moteur public, les diagnostics, le CLI et ESLint. Les tokens personnalisés ne
contournent pas cette protection ; les variantes, marqueurs d’importance ou
classes `leading-*` voisines ne sont pas considérés comme une preuve suffisante.
Les autres familles de corrections restent actives.

`allowTextSizeLineHeightChanges: true` constitue l’unique activation explicite de
l’ancien comportement. Avec l’option absente ou `false`, `text-[12px]` reste intact
et `suggestCanonical` retourne `null`. Le même fichier peut toujours corriger
`p-[16px]` en `p-4`. Les configurations invalides de cette option sont rejetées.

Aucun `leading-[inherit]` n’est ajouté : une telle déclaration pourrait à son tour
entrer en conflit avec un interligne local, et la fusion pourrait supprimer un
`leading-*` antérieur. La documentation, les exemples et le preset ESLint sont
alignés sur le nouveau défaut.

## Validation et qualité des preuves

- **900 tests** : aucun échec ni test ignoré après application du contrat strict (contre 891 avant cette décision).
- Typecheck, lint, knip et build réussis. L’exception knip pour les imports temporaires est limitée au seul script de compilation CSS.
- `pnpm test:css` : **593 conversions valides compilées sous v3**, **677 sous v4**, plus comparaisons ciblées des déclarations CSS, des priorités et des axes en modes horizontal/vertical.
- `pnpm test:compat` : neuf combinaisons ESLint/tailwind-merge réussies sur le tarball final, plus installation sans peers, CLI et consommateur TypeScript strict.
- Vérification de découverte compilée sous **Node 22.6.0**, minimum annoncé : un fichier glob trouvé ; pas de relèvement du minimum nécessaire pour ce changement.
- Audit du lockfile : aucun avis de sécurité signalé. Ce résultat ne couvre pas tous les packages de l’écosystème ni tous les scénarios d’exécution.
- Relecture croisée des changements d’extraction/plugin : cas de corruption rejoués indépendamment ; le cas supplémentaire regex après bloc trouvé pendant cette revue a été corrigé. Une revue indépendante du contrat strict a également validé 780 combinaisons (défaut, `false`, thèmes, tokens, variantes et importance), sans contournement identifié.
- Workflows de cette nouvelle passe modifiés localement, sans déclenchement distant ni publication.

### Performance

La reproduction `cn("p-[16px]")` répétée 8 000 fois passait d’environ **1 780 ms**
à **10 ms** d’analyse, médianes de trois exécutions après échauffement sur la même
machine. Mesure locale de diagnostic, pas engagement de temps sur tous les projets.

Le corpus `static-cn-clsx-cva-v2` utilise des espacements plutôt que des tailles
de texte : 90 fichiers, 3 600 lignes, 10 800 diagnostics. Node 24.22.1, macOS
arm64, Apple M5 Pro. Médianes : analyse fichiers **12,3 ms** ; pipeline
fix/dedup/sort **27,1 ms** ; cohérence **9,2 ms**. Les invariants de diagnostic et
d’idempotence passent ; aucun seuil dépendant de la machine n’est imposé en CI.

## Risques et améliorations restantes

- **Activation typographique explicite** : `allowTextSizeLineHeightChanges: true` peut volontairement modifier le rendu. Le défaut strict laisse les tailles de texte intactes ; il ne transforme pas les autres conventions de thème en preuve générale d’équivalence visuelle.
- **Extraction lexicale polyglotte** : elle reste volontairement bornée. Les expressions calculées, entités HTML ambiguës, spreads et contextes inconnus sont conservés, pas évalués. Les tests ne remplacent pas un parseur complet de chaque langage.
- **Résolution de conflits** : la convention du dernier token n’est pas l’ordre du stylesheet Tailwind. Elle est utile mais peut intentionnellement changer le rendu de classes concurrentes ; la documentation distingue ce contrat de la simple suppression des doublons.
- **Configuration watch** : le module principal est rechargé, mais les helpers importés gardent le cache Node ; leur modification nécessite un redémarrage.
- **Maintenabilité** : l’extraction concentre les règles lexicales de plusieurs langages. Un futur découpage tokenizer/positions de classes/adaptateurs de markup devra préserver le corpus de régressions et les positions de source ; aucun remplacement de dépendance ni découpage purement esthétique n’est introduit ici.

L’absence de serveur, d’authentification et de stockage distant rend un audit
OWASP de routes web non pertinent pour ce paquet. Les risques vérifiés concernent
les transformations de code, le filesystem local, les dépendances et les contrats.
